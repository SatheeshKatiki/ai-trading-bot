## 3. Issue found and fixed today: PyramidSizer scaled into losing PUTs as if winning

The pyramid scale-in above (step 2, price 54.95 — **below** the 55.15
entry) was originally logged as `"Profit hit +0.36%"`. A falling premium
is a loss for a bought PUT, not a profit. Root cause: `PyramidSizer.evaluate_scale()`
had the identical bug already fixed in `exit_engine.py` the night before —
branching on `position.side` using the short-underlying convention,
never checked against 2026-08-03 since that audit only reviewed
`exit_engine.py`, not the sibling `pyramid_sizer.py` (zero test coverage
existed for either, before this week). Net effect: the system would add
capital to a losing PUT position while believing it was compounding a
winner — backwards risk management, one of the more dangerous bug
classes for real money.

Fixed with the identical pattern (`effective_side = 1 if is_option else
position.side`). New `tests/test_pyramid_sizer.py` (6 tests, 0 prior
coverage). Full suite 114/114 after the fix. Full writeup in
`anomaly_log.md`.

Despite the *decision* being wrong, the *quantity bookkeeping* around
this exact scale-in was fully self-consistent (§2 table above) — the bug
affected only whether to scale, not the arithmetic once it happened.

## 4. Operational / infrastructure issues found and fixed today

1. **~20 min of engine downtime during market hours** (09:47–10:07 IST).
   No crash — the process was simply not running when checked, most
   likely from a manual restart of `api_bridge` that wasn't followed up
   with restarting the engine. Restarted clean; state was consistent
   (no reconciliation needed). Underscores the standing no-supervisor
   gap noted in the 2026-08-03 audit.
2. **`engine.log` went silent for ~20 min while the process kept trading
   fine** (10:08–10:31 IST). Root cause: the file handler added
   2026-08-03 was attached at *module import time*, so a test-suite run
   elsewhere attached a second, colliding handler to the same file from
   a separate process, silently breaking the live engine's ability to
   keep writing. Confirmed via `state.db`'s continuously-advancing
   `last_update` that the trading logic itself was completely
   unaffected throughout — this was a pure observability bug. Fixed by
   moving the handler setup into `if __name__ == "__main__":` so only
   the actual live process ever touches the file. Full suite re-run
   (exercises the exact import path that caused this) — 108/108 at the
   time, no regressions.
3. **False alarm, correctly triaged, not "fixed" because nothing was
   broken:** the same test run above left a cluster of alarming-looking
   log lines (a credentials "SECURITY ALERT," a live-mode margin
   rejection, cascading circuit-breaker trips, LSTM loader errors, a
   line stating "today is 2099-01-01"). Cross-checked against
   `state.db`/`active_positions.json` before reacting — confirmed none
   of it was real trading activity (this system runs in paper mode; the
   live-order code path referenced is unreachable here) and that
   `state.db` was not polluted by the test run. Documented so it isn't
   mistaken for a real incident later.
