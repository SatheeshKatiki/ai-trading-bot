**Session:** NSE regular hours, 09:15–15:30 IST. Monitored continuously

This was an unusually eventful day — a process-hygiene outage before the

## 1. Summary

1. **~09:27–09:40 IST — `Start_AI_Bot.bat` launched twice**, producing
   duplicate `api_bridge.py`/`main.py` pairs that collided and all four
   died mid-startup, leaving **zero engine processes running for ~9
   minutes** right at the open. No open position, so nothing went
   unmanaged. Restarted one clean instance of each; no code fix (known,
   still-unguarded gap — a second concurrent launch isn't detected or
   prevented).
2. **10:23 IST — found and fixed a real bug in the 2026-08-12 feed-stall
   watchdog itself.** `api_bridge.py`'s `on_close` WebSocket callback had
   the wrong signature for the vendored Fyers client's calling
   convention (0 args vs. the 1 it's actually called with), crashing on
   every real socket close and silently leaving the feed dead — the
   watchdog's forced-rebuild thread still started, but the crash broke
   the close sequence. One-line fix (`on_close(message=None)`,
   matching the already-correct `on_error` sibling), restarted only
   `api_bridge.py`, live-verified recovery.
3. **Four more upstream WS disconnects through the day (11:30, 12:25,
   12:50, 14:18), all handled correctly** by the fixed code — two
   self-healed via the vendored client's own `reconnect=True`, two via
   the watchdog's forced rebuild, all with clean, fast recovery and no
   repeat of the crash. Investigated a possible thread-leak from
   repeated forced rebuilds after the 4th disconnect's interval
   shortened to 25min; ruled out on available evidence (not fully, for
   lack of a pre-incident baseline).
4. **13:35–13:54 IST — first real trade activity of this validation
   window.** Two full cycles: entry → pyramid scale-in ×2 → trailing-stop
   exit (**+₹178.20**), immediate re-entry → hard SL exit
   (**-₹3,679.00**, PnL math verified exact). Mid-second-position, the
   2026-08-12 `_refresh_fyers_model()` fix fired live for the first time
   with real capital-equivalent risk on the line and worked correctly.
   Portfolio correctly self-halted all further entries after hitting its
   3.46% max daily drawdown (15:14 IST).
5. **14:18–14:57 IST — a ~39-minute total engine freeze, HIGH PRIORITY
   and unresolved.** Not just the tick feed but `engine.log` itself went
   completely silent, including a separate background thread (sentiment
   fetch) that had been running on a fixed cadence all day — pointing at
   the whole process being starved, not a simple feed gap. Very plausibly
   a recurrence of the still-unresolved 2026-08-06 CPU-bound incident,
   this time worse (39min vs. 22min), correlated with an 11-entry DNS
   failure burst and a known, already-flagged-but-unfixed gap
   (`main.py` calls `broker.get_market_data()` synchronously on the
   event loop with no throttle). No open position during the window
   (incidental timing). Not fixed — found minutes before market close.

## 3. Root causes (condensed — see `anomaly_log.md` for full detail)

1. **Duplicate `Start_AI_Bot.bat` launch, no concurrent-instance guard.**
   Two full launches produced 4 engine processes that collided and all
   died. No code change — still an unguarded gap, same class as a
   2026-08-03 incident.
2. **`api_bridge.py`'s `on_close(message=None)` signature bug.** The
   vendored `fyers_apiv3` client calls `on_close` as `self.OnClose(message)`;
   a 0-arg local definition raised `TypeError` on every real socket
   close, breaking the 2026-08-12 watchdog's own recovery path the first
   time it hit a real close. Fixed, then validated across 4 more real
   disconnects the same day with zero repeat crashes.
3. **~39-minute total process freeze, root cause not confirmed.** No
   `py-spy` dump was captured during the freeze itself. Circumstantial
   evidence (DNS failure burst + `main.py`'s known-unthrottled,
   synchronous `broker.get_market_data()` calls on the event loop, a gap
   explicitly flagged but "deliberately not acted on" in the 2026-08-03
   audit) points at a repeat of the 2026-08-06 CPU-bound incident, but
   this is a hypothesis, not a confirmed diagnosis.
